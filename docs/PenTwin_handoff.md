> 対象：本プロジェクトを引き継ぐLLM（以下「あなた」）
> 作成日：2026-10-26
> ステータス：構想・設計段階。コードは未着手。

## 0. 最初に読むこと（必須の作業順）

1. **実装を始める前に、本書の設計を敵対的にレビューすること（第1章）。** レビュー結果を `REVIEW.md` として書き出し、依頼者の承認を得てから実装に入る。
2. **最優先は「品質」。** ここでの品質とは「生成された文章が、依頼者本人の論文文体として本人と第三者に見分けがつかないこと」かつ「内容を歪めないこと」。速度・機能数・対応範囲は品質より常に下位。
3. **ローンチ形態は MCP サーバーのみ。** Webアプリ、ブラウザ拡張、Word/Overleafアドイン、SaaS、独自UI、独自チャットは作らない。提案もしない（範囲外として記録するのは可）。
4. 本書中の **【未検証】** は、作成時点で裏付けを取っていない事項。実装前に一次情報（公式仕様・公式ドキュメント）で確認すること。

## 1. 敵対的レビュー（最初のタスク）

### 1.1 目的

本書の設計は、会話の中で短時間に組み立てた仮説である。あなたの役割は、それを擁護することではなく **壊すこと**。「この設計では品質目標を達成できない」と言える根拠を最大限探し、致命的な欠陥を実装前に潰す。

### 1.2 レビューのルール

- 立場：**懐疑的な査読者**。「よくできている」で終わるレビューは不合格。
- 各指摘に **重大度** を付ける：`BLOCKER`（このままでは品質目標に届かない）/ `MAJOR`（品質を大きく下げる）/ `MINOR`。
- 各指摘に **根拠** を付ける：一次情報、論文、再現できる小実験、または論理。推測のみの指摘は「仮説」と明記。
- 各指摘に **代替案** と、その代替案の弱点を付ける。
- 「わからない」ものは検証実験の計画として書く（何を、どのデータで、何をもって合否とするか）。
- 依頼者の決定事項（第2章）は前提として扱うが、品質を損なうなら **異議として明記してよい**。黙って変えない。

### 1.3 必ず攻撃すべき論点

| # | 論点 | 問い |
|---|---|---|
| R1 | 品質の定義 | 「本人らしさ」を何で測るのか。数値指標（特徴量距離）は本人の主観と相関するのか。相関しないなら指標を最適化するほど悪化する（グッドハートの法則）のでは？ |
| R2 | 特徴量採点の妥当性 | 文長・文末・接続詞の分布を合わせても「らしさ」は出るのか。分布は合っても不自然な文（指標ハック）にならないか。 |
| R3 | 対訳データ（平凡版→原文）の偏り | 平凡版はLLMが作る。その「平凡さ」は、本番で書き直す対象（LLMの下書き）と同じ分布か。ずれていれば学習も評価も的外れになる。 |
| R4 | 評価の循環 | 同じLLM系列で生成・判定・平凡版作成をすると、評価が甘くなる。どう分離するか。 |
| R5 | 内容の歪み | 文体を寄せる過程で、数値・主張の強さ・限定条件（hedge）が変わる危険。論文では致命的。どう検出するか。 |
| R6 | データ量 | 本人の論文が数本しかない場合、統計的に安定したプロファイルが作れるか。最小必要量はどれくらいか。 |
| R7 | 役割（move）ラベルの精度 | LLMによる自動ラベル付けの誤りが実例選択の質を決める。誤りはどれくらいで、どう補正するか。 |
| R8 | 自己剽窃 | 実例を見せると原文の言い回しが流用される。どの閾値で止めるか。逆に、止めすぎると「らしさ」が消えるのでは？ |
| R9 | MCPという器の限界 | 生成は利用者側のLLM（Claude等）が行う。サーバー側から品質をどこまで強制できるか。ループ（書く→採点→直す）をLLMが守らなかったら？ |
| R10 | クライアント差 | Resources / Prompts / Sampling の対応はクライアントごとに異なる【未検証】。Toolsのみで品質ループを成立させられるか。 |
| R11 | 言語 | 日本語と英語で特徴量も解析器も違う。両対応は品質を薄めないか。初期は片方に絞るべきでは？ |
| R12 | 過去の癖の扱い | 古い論文の癖、査読対応で仕方なく入れた表現まで再現してしまう。本人が「残したい癖」をどう指定するか。 |
| R13 | 再現性 | 同じ入力で毎回同等の品質が出るか。LLMのバージョン変更にどう追従するか。 |
| R14 | プライバシー | 未発表原稿・個人の論文コーパスをどこに置き、何をLLMに渡すか。 |

### 1.4 レビューの成果物

`REVIEW.md` に以下を含める：

1. 指摘一覧（重大度・根拠・代替案）
2. 設計の修正提案（本書のどこをどう変えるか）
3. 検証実験の計画（第7章の評価計画への追加・修正を含む）
4. 依頼者に判断を仰ぐ事項のリスト（最大5件、選択肢付き）

## 3. 背景：なぜ作るか

- 調べた範囲では、Paperpal・Jenni AI・Writefull などの学術執筆ツールは引用・校正には強いが、**本人の過去論文から文体を学習して寄せる機能は確認できなかった**。
- Grammarly のボイス機能は自動で文体を判定するが英語中心で、Business/Enterprise向け。学術論文の章構成や役割までは扱わない。
- ChatGPT / Claude に「文体ガイド」を渡す方法は手軽だが、形容詞ベースの説明は解釈がぶれ、**再現性が低い**。
- PenTwin の狙いは、文体を **数値・実例・規則・採点ループ** で表現し、どのMCP対応LLMからでも同じ品質で使えるようにすること。

---

## 4. 設計の中心となる考え方

1. **文体は「話題」ではなく「段落の役割」に強く表れる。** 実例は章と役割（move）で選ぶ。
2. **説明より実例。** 形容詞の説明文より、場面が合った本人の原文を見せるほうが効く。
3. **採点はLLMの感想ではなく数値で。** LLMは自分の出力を甘く評価しがち。
4. **「平凡な文 → 本人の原文」の対訳** で、書き直しという具体的な作業として学ばせる。
5. **内容は一切変えない。** 文体変換で数値・主張の強さ・限定条件が変わったら失敗とみなす。

## 5. システム構成

```
[本人の過去論文（PDF / Word / LaTeX）]
        ↓ 取り込み（初回のみ。CLIで実行）
 ① テキスト化 → 章分け → 段落ごとに役割（move）ラベル
 ② 文体の数値プロファイル作成
 ③ 用語・表記の辞書作成
 ④ 対訳データ作成（平凡版 → 原文）
 ⑤ 評価用データの取り分け
        ↓
[PenTwin MCPサーバー（ローカルで動作）]
  Tools（中心）／ Resources ／ Prompts
        ↓
[MCP対応クライアントのLLM]
  書く → 採点 → ずれた所だけ直す → 内容の忠実性確認 → 重複確認
```

### 5.1 取り込みパイプライン

| 段階 | 内容 | 技術候補 |
|---|---|---|
| テキスト化 | 本文・見出し・図表キャプションを分離。参考文献・数式・表は除外または別扱い | LaTeX原稿があれば最優先。PDFは GROBID / Marker / Nougat【比較検証が必要】 |
| 章分け | 序論・方法・結果・考察・結論など | 見出しの正規化 ＋ LLMによる補正 |
| 役割ラベル | 段落ごとに move を付与。序論は Swales の CARS モデルを基本に、考察は「結果要約／先行研究比較／解釈／限界／今後」など | LLMで自動付与 → 本人が確認できる形式（CSV等）で出力 |
| 文の分解 | 形態素・品詞・係り受け | 日本語：SudachiPy / GiNZA、英語：spaCy |
| 保存 | 段落・ラベル・特徴量・ベクトル | SQLite ＋ sqlite-vec（または Chroma） |

### 5.2 文体の数値プロファイル（`style_profile.json`）

章別・役割別に分布として保持する（平均だけでなくばらつきも）。

- 文の長さ（文字数／語数）の分布
- 文末表現の比率（「である」「と考えられる」「示唆される」、体言止め など）
- 接続表現の頻度と位置
- 断定の強さ：ぼかし表現と強い断定の比率
- 受け身の比率、名詞化の頻度、読点・括弧の密度
- 段落あたりの文数、段落の最初の文が要点を述べているか
- 機能語の頻度分布（著者を識別する研究で有効とされる指標）

プロファイルは版管理し、論文の年代で重みを付けられるようにする。

### 5.3 用語・表記の辞書（`lexicon.yaml`）

- 使う語／使わない語
- 表記の統一（送り仮名、全角半角、単位、略語の初出の書き方）
- **AIらしい定型表現の禁止リスト**
- 本人が「残したい癖」「やめたい癖」のフラグ

ここはLLMに判断させず、プログラムで決定的にチェックする。

### 5.4 対訳データ（`pairs.jsonl`）

1. 本人の段落を、LLMに「内容は変えず、ありふれた文体に書き直して」と指示して平凡版を作る
2. （平凡版, 原文, 章, 役割）の組を保存
3. 用途：実例として提示／評価用データ／将来のLoRA学習データ

**注意（R3）：** 平凡版の分布が、本番で書き直す下書きの分布とずれる危険がある。平凡版の作成には複数のLLMを使うことを検討。

## 6. MCPサーバー設計

### 6.1 方針

- **Toolsを中心に設計する。** Resources / Prompts / Sampling はクライアント対応が揃っていない可能性がある【未検証】ため、それらがなくても品質ループが成立するようにする。
- サーバーはローカル（stdio）で動かし、論文コーパスを外部に置かない。
- 取り込み処理は重いので、MCPツールではなく **CLI**（`pentwin ingest` など）で実行する。CLIは取り込み専用の補助であり、ローンチ対象はMCPサーバーのみ。

### 6.2 Tools

| ツール | 入力 | 出力 | 目的 |
|---|---|---|---|
| `get_exemplars` | 章、役割、要点（任意）、件数 | 本人の原文段落と、その対訳 | 場面に合ったお手本を提示 |
| `get_style_brief` | 章、役割 | その場面の文体要約（数値の目標値と短い指示文） | 書く前の指示 |
| `score_style` | 下書き、章、役割 | 特徴量ごとの値・目標値からのずれ・総合点 | 数値で採点 |
| `diff_report` | 下書き、章、役割 | 「文末の『と考えられる』が目標より多い」など、直すべき点の具体的な指示 | 採点結果を修正指示に変換 |
| `check_lexicon` | 下書き | 違反箇所と置き換え案 | 表記ルールの決定的なチェック |
| `check_fidelity` | 元の下書き、書き直し後 | 数値・固有名詞・否定・限定条件・主張の強さの変化 | 内容の歪みの検出（R5） |
| `check_overlap` | 下書き | 過去論文と一致する連続した語の箇所 | 自己剽窃の防止（R8） |
| `finalize` | 下書き、章、役割 | 上記チェックをまとめた合否判定と記録ID | ループの最後の関門 |

### 6.3 Resources（使えるクライアント向けの補助）

- `pentwin://guide` 全体の文体ガイド
- `pentwin://profile` 数値プロファイル
- `pentwin://lexicon` 辞書
- `pentwin://section/{章名}` 章別の書き方

### 6.4 Prompts（使えるクライアント向けの補助）

- `write_section(章, 役割, 要点)`
- `restyle(下書き)`
- `review_draft(下書き)`

### 6.5 品質ループ（必須の手順）

```
1. get_style_brief と get_exemplars で場面の手本を得る
2. LLMが下書きを書く
3. score_style ＋ check_lexicon で採点
4. 目標に届かなければ diff_report の指示に従って該当箇所のみ修正（最大2回）
5. check_fidelity で内容が変わっていないか確認（変わっていたら差し戻し）
6. check_overlap で流用がないか確認
7. finalize で合否と記録を残す
```

**未解決（R9）：** LLMがこの手順を省略する可能性がある。ツールの説明文で手順を明示する、`finalize` を通らない出力は「未検証」と表示させる、などの対策を検討すること。

## 7. 品質の定義と評価計画

品質を最優先とするため、**評価の仕組みを機能より先に作る。**

### 7.1 品質の構成要素

| 要素 | 意味 | 測り方（案） |
|---|---|---|
| 本人らしさ | 本人の文体と見分けがつかない | ①特徴量の距離 ②本人の文と他人の文を見分ける分類器で「本人」と判定される率 ③**本人による盲検評価**（最も重視） |
| 内容の忠実性 | 数値・主張・限定条件が変わらない | `check_fidelity` ＋ 人手確認 |
| 自然さ | 指標を満たすために不自然になっていない | 第三者（または別系列のLLM）による盲検評価 |
| 安定性 | 同じ入力で毎回同等 | 同一条件5回生成の点数のばらつき |
| 非流用 | 過去論文の丸写しがない | 連続一致語数の上限 |

### 7.2 評価データ

- 対訳データの約2割を評価用に取り分け、開発中は一切見せない。
- 評価用の段落は「論文単位」で分ける（同じ論文の段落が学習側と評価側に分かれると評価が甘くなる）。

### 7.3 合格基準（案。レビューで見直すこと）

- 本人の盲検評価：本人の原文と生成文を並べて、本人が原文を当てられる率が偶然に近いこと
- 内容の忠実性違反：0件
- 自然さ：第三者評価で原文と有意差なし
- 判定に使うLLMは、生成に使うLLMと別系列にする（R4）

### 7.4 回帰テスト

モデルのバージョン、temperature、プロファイルの版を記録し、変更のたびに評価セットで点数を比較する。点数が下がる変更は採用しない。

## 9. スコープ

### 対象

- ローカルで動くMCPサーバー（stdio）
- 取り込み用CLI（MCPサーバーの準備のための補助）
- 評価用スクリプト

### 対象外（作らない）

- Webアプリ、SaaS、ホスティング
- ブラウザ拡張、Word / Google Docs / Overleaf アドイン
- 独自のチャットUI・エディタ
- 複数ユーザー管理、課金
- 初期段階でのモデル追加学習（評価で必要性が示されるまで）

## 10. 実装の順番（案。レビュー後に確定）

| 段階 | 内容 | 完了条件 |
|---|---|---|
| 0 | 敵対的レビュー（第1章） | `REVIEW.md` を依頼者が承認 |
| 1 | 取り込み・役割ラベル・評価データの取り分け | 依頼者の論文で抽出精度を目視確認 |
| 2 | **評価の仕組み**（第7章） | 原文同士・素のLLM出力で基準点を測定 |
| 3 | `get_exemplars` / `get_style_brief` | 基準点からの改善を評価で確認 |
| 4 | `score_style` / `diff_report` / `check_lexicon` と品質ループ | 改善が統計的に確認できる |
| 5 | `check_fidelity` / `check_overlap` / `finalize` | 忠実性違反0件 |
| 6 | 主要クライアントでの動作確認とパッケージ化 | 依頼者の環境で導入できる |

各段階で「素のLLM」との比較を必ず行い、改善が確認できない機能は捨てる。

## 11. リスクと既知の弱点

- 指標の最適化が「らしさ」と一致しない可能性（R1, R2）
- 対訳データの平凡版の分布のずれ（R3）
- 生成はクライアント側のLLMが行うため、サーバーから品質を強制しきれない（R9）
- 過去論文の本数が少ないと、プロファイルが不安定になる（R6）
- 過去の癖（望まないもの）まで再現する（R12）
- 自己剽窃と「らしさ」のトレードオフ（R8）
- 未発表原稿の扱い（R14）：コーパスはローカルに置き、LLMには必要な断片のみ渡す

## 12. あなたへの最初の指示（まとめ）

1. 本書を通読する。
2. 第1章に従い、敵対的レビューを行って `REVIEW.md` を作る。
3. 第2章の未決事項と、レビューで出た判断事項を、選択肢付きで依頼者に確認する。
4. 承認後、第10章の段階0→1の順に進める。**評価の仕組み（段階2）より前に生成機能を作り込まないこと。**
5. 迷ったら品質を優先する。品質を下げる近道は採らない。
